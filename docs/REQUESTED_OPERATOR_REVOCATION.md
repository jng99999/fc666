# Global credential revocation for existing requested-Paper operators

The existing23 protected POST routes under /api/v1/paper-requested/ now enforce global credential denies from segmented_operator_revocations. This is a new HTTP admission layer; it does not rewrite revocation records, frozen financial/control/source/ownership contracts or account capacities. Only rows with ledger_id=* and action=* apply to this legacy namespace. Segmented account/action-specific denies retain their declared scope and are not reinterpreted as legacy grants or denies.

The operator still needs its existing configured bearer credential and explicit account/action/pool grants. Wrong credentials, missing configuration, invalid request models and denied grants retain their existing pre-storage behavior. After model validation and account/action/pool scope checks, the protected endpoint acquires the shared database revocation fence and audits retained denies before invoking the original financial/inspection implementation. A global deny produces401 with WWW-Authenticate:Bearer and Cache-Control:no-store. Corrupt/unavailable revocation state fails closed with sanitized409/503. No credential or underlying database error is echoed.

The wrapper holds the shared database transaction lock through the original endpoint call and response construction, releasing it before sending the response. Revocation's exclusive lock waits for earlier admitted operations or fails at its existing2-second lock timeout. Original command retries also pass through the fence: an already recorded financial effect is preserved, but a withdrawn credential cannot use a retry to bypass the deny. Direct trusted internal calls and existing public read-only GET inspection endpoints remain outside this HTTP operator fence. Process-local policy replacement still applies only to segmented routes; legacy allow policies remain startup configuration and must be rolled out securely for rotation/grant changes.

The protected router has an explicit path/action catalogue covering control, finalization, onboarding, previews, source ingestion, ownership, dispatch/assessment, health, staged inbox, multi-account exposure and pool operations. Unknown protected registration or methods fail rather than silently adding an unfenced operator endpoint. Tests enumerate public OpenAPI request schemas and send valid request models to every registered protected POST; no route-count-only readiness claim is made. The original handler retains its own grants and domain gates as well.

All participating API processes must run this code and use the same revocation database. Updating source or pushing the branch does not deploy other running hosts. Sustained load, distributed deployment acceptance, durable allow-grant/user identity management and public release remain unfinished. No new schema, dependency, credential, domain, frontend build or service is required; restart only owned API and run existing readiness checks. Tests use artificial credentials and isolated databases; never revoke a real main credential for demonstration.
