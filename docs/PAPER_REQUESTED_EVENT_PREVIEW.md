# Scoped local source-event preview

POST /api/v1/paper-requested/event-previews is a default-disabled read-only route with the independent PREVIEW_EVENT operator grant and exact account membership. Other grants do not imply it. It accepts strict account_id/request_id, financial/control revisions, source and event fields. Source must explicitly be {kind:LOCAL_PAPER_OPERATOR_INPUT,source_id:bounded local label}. This labels the proposed input, not the original stored event's provenance or an authenticated venue message. EXCHANGE_VERIFIED and other claimed remote origins are rejected. Existing secure single-operator configuration guidance applies; no production token/grant is installed.

The event envelope has event_id, matching request_id, strict sequence0..999, aware received_at, kind and payload. Supported kinds follow the original contract: SUBMIT, ACK, UNKNOWN_SUBMISSION, CANCEL_REQUEST, CANCEL_ACK, REJECT, FILL, RECEIPT and SEAL. Exact payload fields, Decimal bounds, cumulative totals, duplicate identities, event order and clocks are checked by that unchanged contract. Financial/control history is captured together under the account lock; both expected versions and controlled coverage must match. A fresh SUBMIT projection also recomputes the existing full-request control/risk gate. Other receipts/late fills remain projectable after PAUSE/STOP; this grants no new-work or resume authority.

The paper-requested-event-preview-v1 report contains complete financial export and controls, source/event proposal, classification, admission if applicable, projected_request_summary, projected_account, projected_active_request_id and projected_financial_revision. event_persisted=false and external_submission_allowed=false are mandatory. No event, provenance row, gate, balance, revision, seal or reservation release is persisted. SUBMIT is hypothetical; UNKNOWN_SUBMISSION keeps its hold; a projected SEAL release is not an actual release. State/counters/amounts describe a possible reduction of explicit local inputs, not observed trading.

NEW_LOCAL_INPUT folds one next source event only for the active request within capacity. EXACT_EVENT_REDELIVERY requires an exact existing event and performs no additional folding or revision advance. Its request-specific summary may describe an older sealed request; projected_account and active_request_id always preserve the current account and a later request, rather than restoring that old request's balances. Conflicting duplicate deliveries, gaps, sealed/voided new inputs and fabricated cumulative receipts fail. This is only a forecast at one captured checkpoint; state may change immediately afterwards and future ingestion must recheck inside its write transaction.

Offline verification: python -m scripts.verify_requested_event_preview FILE. It independently reconstructs financial/control snapshots and re-evaluates classification, admission, cumulative financial effects, duplicate preservation and flags. Unsupported versions, inconsistent rehashed facts, duplicate JSON keys and over32MiB reports fail. Financial v1 and void-containing v2 snapshots retain existing formats. Consistency hashes are not signed origin, freshness, authenticated completeness or proof of a prior server call. Changing an otherwise valid caller source label cannot authenticate it.

Disabled503, authentication401, grant403 precede storage; authorized missing account404, revision/rule/event/evidence conflict409, and storage/lock failure503 use generic no-store responses. Strict body errors retain standard422. The existing two-second read lock timeout bounds lock waiting only. No schema, dependency, frontend, service or network change. Main requested tables remain empty and Live stays disabled.

Default-disabled local ingestion and immutable receipts are now implemented separately; see PAPER_REQUESTED_SOURCES.md. PREVIEW_EVENT remains read-only and does not grant INGEST_EVENT. Exchange message authentication, private connectors, external submission/ownership, actor identity, shared capital and scheduling remain incomplete. The SQLite submission laboratory stays isolated from PostgreSQL capital.
