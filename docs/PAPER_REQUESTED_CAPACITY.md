# Local requested-engine capacity

The current admission path requires at least three remaining source-event slots before a new request can reserve capital. The minimal complete history is SUBMIT, full FILL (or REJECT), SEAL. This applies to ordinary journal preparation, server preparation previews, pooled preparation previews and new pooled commands. It does not change event acceptance, reject already submitted economic facts to save space, release holds or evict evidence. The existing100-request and1000-account-event limits remain.

The guard is deliberately separate from frozen preparation-preview-v1 replay. Historical previews and admissions created under the former policy remain verifiable; exact retries acknowledge their original hold even if current admission would refuse them. An offline v1 preview is not proof that current server admission accepts its checkpoint. New ordinary commands check the stronger gate inside `_prepare`; pooled commands check after their original-receipt retry branch and under the pool/member locks.

`core.paper.requested_capacity.capture(engine, account_id)` reads a fully audited, locked account with a2-second lock timeout, then returns `paper-requested-capacity-v1`. The report freezes100 requests and1000 events, includes the complete journal, remaining slots, capacity fit for new/idle accounts, and active-request funding and shortest structurally valid terminal path. A created request needs3 events; a submitted unresolved or partial request can, in the best case, reach terminal evidence and SEAL in2; full fill/cancel/reject evidence needs1 SEAL. A best-case remaining fill or rejection/cancel fact is not promised. Original UNKNOWN/cancel holds remain explicit.

`future_settlement_guaranteed=false`, `submission_allowed=false` and `read_only=true` are unconditional. Capacity fit does not grant risk/control/scope permission. Reports provide internal consistency, not authenticated venue origin, current data health or signed server provenance. Verification recomputes the whole report, including flags/limits, after complete journal replay. Offline CLI: `uv run --frozen python -m scripts.verify_requested_capacity FILE`; input is bounded32MiB and duplicate JSON keys are rejected. No capacity HTTP route or frontend was added.

This is initial structural admission headroom, not a full lifecycle capacity guarantee. Arbitrarily many partial fills or repeated intermediate receipts can still exhaust the retained journal. Legacy requests may already have insufficient headroom; preserve their evidence and holds. Archive/rollover, durable overflow settlement and freshness/health gates must be designed before scheduling or external transport. No simulated fixture balances are inserted into the main database.
