# Revocation retained-chain checkpoint (schema0030)

The singleton segmented_operator_revocation_head stores the retained count plus original root and current head hashes. Every revocation read, write and original retry verifies this checkpoint against the fully replayed immutable records. A missing chain tail, empty records after prior revocation, missing checkpoint row or altered root/head/count blocks both segmented access and the legacy global-deny fence. Runtime never creates a missing checkpoint or treats corrupt evidence as a fresh empty deny list.

The checkpoint advances by exactly one with each new immutable revocation, in the same PostgreSQL transaction and exclusive admission/revocation lock. Its root cannot change after the first record; deletion and nonmonotonic transitions are rejected by database triggers. An insert or checkpoint update failure rolls back both state changes. The existing original-command retry path changes neither count nor hash. Limits remain1024 records/4KiB per record; no financial/worker capacity or revocation scope changes.

Migration0030 locks the shared revocation namespace/table and independently validates the retained0029 chain using frozen v1 rules before creating the singleton. It imports no mutable application validator, rewrites no original payload/hash and preserves existing denies. Corrupt/incomplete retained lineage causes migration rollback. An empty genuine source initializes count0/null hashes. Initialization anchors the verified retained state; it cannot infer a previously missing complete chain tail before a checkpoint existed. Populated or missing-checkpoint downgrade refuses to discard the anchor. Full empty-schema migration roundtrip remains supported.

API schema readiness requires the singleton row to exist. Protected admission additionally verifies full chain/checkpoint consistency; dependency readiness alone does not certify authorization evidence or production acceptance. Complete PostgreSQL backup/restore includes the new table and checks all table-content hashes; original revoked credentials remain denied after restoration. Hashes/anchors in the same database do not authenticate privileged replacement of both checkpoint and records, or establish freshness when an older complete coherent backup is restored. Recovery still requires an externally trusted current checkpoint and independent storage/rollout acceptance.

Tests simulate missing tails, all records missing, deleted/altered checkpoints, an actual checkpoint-update transaction failure, immutable/monotonic guard refusal and valid/corrupt populated0029 upgrades using isolated databases. Existing SIGKILL, original retry, shared-lock concurrency, global-route deny and populated restore checks run with the new checkpoint. No main revocations are seeded to demonstrate the feature.
