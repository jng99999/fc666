# Persistent segmented operator revocation

Schema0029 adds immutable `segmented_operator_revocations`. The two segmented HTTP endpoints now check this database deny list at admission, in addition to configured credentials and current process-local account/action grants. Recreating the API or reusing the startup token cannot undo a committed revocation. All participating API processes must run this code and connect to the same database. Legacy command routes and trusted internal financial/worker library calls are outside this fence.

Trusted embedded administration may call `app.state.segmented_operator_access.revoke('stable-command-id', ledger_id='*', action='*')`. It revokes the installed configured credential, without accepting or displaying a plaintext token argument. The library primitive is segmented_revocations.revoke for trusted internal callers. No public management endpoint, shell token argument, credential generation or automatic main-account enrollment is supplied. Use command/account labels that contain no secrets.

The subject is a domain-separated SHA256 fingerprint of the configured bearer token; raw credentials are not stored as credential fields. A global */* deny produces401, while a matching account/action deny produces403. Scopes support exact ledger IDs or *, and READ_SEGMENTED_EVIDENCE, ENROLL_SEGMENTED_WORKER or *. Denies are permanent for that credential: removing an in-memory restriction cannot restore it. A different securely configured token is a different subject and still requires explicit account/action grants. Token entropy, secure credential distribution and rotation remain operator configuration requirements.

Global PostgreSQL advisory locks order operations: admitted segmented requests hold a shared transaction lock through the protected operation; revocation obtains the exclusive lock. An earlier admitted operation may complete, and revocation waits or fails at the2-second database lock timeout; later admissions observe the committed deny. Same-process policy replacement additionally retains its existing process lock. Revocation failure does not establish that a deny was committed; exact original command retry returns the same committed record, while conflicting identity/scope and a duplicate scope under a different command ID fail. No existing financial effect is retroactively cancelled.

The immutable sequence/hash chain is bounded at1024 records of at most4KiB database JSON each. The table stores subject fingerprint, explicit scope, command identity and database time. Reads verify retained record/SQL metadata, sequence, predecessor hashes, bounds and clocks. Sequence gaps/corrupt retained evidence, unavailable tables/database and lock failures block the protected operation. Triggers forbid record updates/deletion; populated downgrade refuses evidence loss. Direct privileged database modification or restoring an older complete consistent backup cannot be authenticated by these hashes. Backup recovery must compare the complete table catalogue/hashes and expected current checkpoint; independent-storage and infrastructure freshness acceptance remain pending.

The guard uses one database connection/transaction in addition to the existing financial operation connection. Connection-pool sizing, sustained load and deployed distributed-process acceptance remain pending. No cross-database synchronisation, user/role registry, durable allow-grant history or authenticated source/control/health/pool/scheduler integration is supplied. Financial and local-worker operational archives retain their declared scope and do not export global operator revocations; populated database backup/restore covers the new table.

Restoration: preserve .env and volumes, stop only owned API, run bash scripts/start.sh to migrate current head0029, then verify all five services and `.venv/bin/alembic check`. Existing frozen installation/start instructions still apply. No new dependency, credential, network domain, frontend build or service is needed. Tests revoke only artificial tokens in isolated databases; do not create revocations in the main database to demonstrate the feature.
