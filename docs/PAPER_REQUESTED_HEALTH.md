# Opt-in persisted local data-health gates

Schema0024 adds an irrevocable `health_version` declaration, immutable account health policies and immutable request/phase gates. Existing accounts keep NULL declaration and unchanged financial/export/control versions; no historical health admission is invented. Internal `requested_health.enroll(engine, account_id, expected_control_revision)` requires a controlled account at financial revision0 with a supported canonical Binance Spot instrument. The server derives a fixed policy from its immutable opening and explicit control checkpoint. Retry returns the original enrollment even after later activity; conflicting checkpoints fail. Database guards forbid removing/changing the marker, retrofitting requests, changing financial state during enrollment or deleting/updating policies/gates. Populated downgrade is refused; empty roundtrip is supported.

For enrolled accounts, new PREPARE and first SUBMIT require a trusted backend `health_cache` dependency. There is no client-supplied health JSON approval. Capture reads current public quality using the existing Redis/PostgreSQL diagnostic. Its instrument must equal the account declaration and its rules must numerically equal the frozen request's tick/quantity/minimum rules. Both BUY and SELL use the same health gate. The immutable receipt binds policy, full request, original controlled-risk gate, quality evidence, phase and database microsecond checkpoint; external submission remains false.

At most2 seconds may separate observed report time and database checkpoint, with the same bounded clock-skew tolerance. Data timestamps/bar continuity are independently reevaluated at the database checkpoint, preventing a newly generated report from hiding already expired underlying observations. The same predicate is checked immediately before returning from the journal write; a stale/unhealthy result rolls back the transaction. This is not a guaranteed future market state or a database-enforced wall-clock deadline at physical commit.

The request/reservation/PREPARE-risk gate/health gate commit together. Pool preparation also commits its mandatory shared admission in that transaction under existing pool/all-member locks. SUBMIT/event/risk/health/source/owned dispatch commit together. Internal optional dependency is forwarded by journal, controlled preparation, pooled preparation, source acceptance and owned delivery. Missing providers fail closed for enrolled new work. Existing HTTP routes do not supply that dependency, so they cannot prepare/submit enrolled accounts until a separately scoped integration is added; no HTTP health enrollment or new grants are added in this slice. Financial previews remain forecasts, not health approvals.

Exact preparation/SUBMIT/source retries return original evidence before new health acquisition. Reads verify historical checkpoints rather than applying today's market state. Late fills/receipts/seals and permitted local finalization remain available after unhealthy data or STOP; no automatic hold release or cancellation is invented. Every journal audit requires exactly one health gate per recorded controlled PREPARE/SUBMIT, bound to the immutable request and replayed risk checkpoint. Undeclared orphan or missing declared evidence fails closed. SQL checks32KiB policy and32MiB aggregate gate storage before loading; each gate is bounded256KiB. Budget overflow rolls back new evidence and holds.

`scripts.verify_requested_health_gate FILE` verifies the bounded, duplicate-key-safe historical health predicate and declared bindings. It does not authenticate the risk actor/venue, validate the entire account/control history or prove current freshness. Server audit separately binds receipts to complete financial/control replay. No new scheduler, exchange credential, private transport, account funding or product fixture data is introduced. Public book/source validity and instrument refresh remain the limitations documented in MARKET_DATA_QUALITY.md. Next: independently scoped health enrollment/read and server-owned provider integration for authorized HTTP commands, then broader retention and production work.
