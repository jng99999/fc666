# Immutable local capital pools and coherent captures (head0022)

The internal PostgreSQL library `shared_capital_pool.create(engine, definition)` persists an immutable pool definition and canonical immutable membership. `capture(engine,pool_id,candidate=None)` produces a bounded offline-replayable wrapper around the existing fixed-allocation forecast. There are no HTTP pool writes, new grants, actual shared reservations or private transport.

Creation requires all member accounts to exist, have untouched financial openings (revision0) and match the declared quote-only allocations. A globally unique account member key excludes membership in a second pool; no reassignment/removal is supported. Definitions cannot change on retry. Exact retries audit existing membership/accounts and remain valid after later account activity. Constructors share a bounded-wait transaction advisory lock to serialize overlapping memberships and a100-pool limit. New definitions and members commit atomically; missing/changed declared membership fails closed without repair.

Capture locks the immutable pool row, acquires all member account row locks in canonical account order, then audits any member. Concurrent financial/control/ownership writes cannot change a locked member during the capture. Accounts locked earlier remain unchanged while later locks are acquired, so a common locked state exists before auditing. READ COMMITTED is sufficient for these protected account namespaces; this is not a global exchange snapshot, freshness proof or isolation of unrelated services. Lock timeout is2s; no partial report is returned.

Schema0022 adds paper_capital_pools and paper_capital_members with foreign keys, global account exclusivity, ordered membership uniqueness and UPDATE/DELETE rejection. Populated downgrade is refused; empty migration roundtrip is supported. Member association with quote/instrument and initial funding remains declared local configuration, not authenticated venue metadata. Existing per-account prepare/ingest paths do not enforce the pool cap: this stage observes pool risk and does not implement atomic shared admission.

Capture wrappers state coherent_capture_supported=true and exclusive_pool_membership_supported=true for the server's supported database path. The nested frozen pure forecast correctly retains unsupported flags, because the pure function alone does not establish either guarantee. Offline verification replays internal evidence and validates the declaration; it cannot authenticate that a producer actually held database locks or obtained data from this server. Neither layer authorizes submission or commits shared reservations.

Aggregate input/output is bounded32MiB with up to100 members; each member audit is also bounded. These limits are not a whole-process memory budget. `python -m scripts.verify_shared_capital_pool report.json` verifies a capture offline with duplicate-key and input bounds. No dependencies, hosts, secrets or frontend changes. Main stays empty and Live disabled.
