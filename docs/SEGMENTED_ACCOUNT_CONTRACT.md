# Complete segmented account replay

`paper-requested-segmented-account-v1` is a read-only prerequisite for future versioned financial application. It chains up to100 explicit requests from one verified account/instrument opening, with at most8192 source events across the entire account and32MiB of input/export evidence. Per-request segmented limits are preserved. A next request must use the exact previous settled base, a unique request/client identity and a nonregressing clock. An unsealed pending, submitted, cancellation-acknowledged or unknown-outcome request prevents the next request; its full remaining hold survives replay.

Each account entry binds its ordinal, predecessor hash, independently verified single-request segmented report, optional original unsubmitted-finalization receipt, effective settlement summary and cumulative account revision. The final account, active request, clock, event/finalization counts and revision are independently reconstructed. Entry `summary` includes any explicit local withdrawal; the embedded report retains its original unwithdrawn single-request arithmetic. No ordinary cancellation acknowledgement releases funds. Original frozen finalization requires zero source events, matching pre-finalization revision/clock/request hash and a unique command; submitted requests cannot be locally withdrawn. Fill identities remain request-scoped, matching existing settlement contracts; cross-segment duplicates within a request do not duplicate fills.

`from_journal` verifies the complete frozen v1/v2 journal before converting it, then compares balances, active request, clock, revision and event count exactly. `capture` uses existing bounded PostgreSQL account-lock/audit reads. This does not increase the existing database's1000-event capacity, persist new financial rows, create grants or expose an HTTP write route. It is a verified projection of existing local financial history, not an authenticated exchange receipt or current worker permission. New independent replay histories beyond the frozen database capacity are still only offline evidence.

Verify a complete export using `.venv/bin/python -m scripts.verify_segmented_account FILE`. The CLI caps reads before parsing, rejects duplicate/nonfinite JSON and reports generic failures without raw input. Hashes detect internal inconsistency; resealing fabricated balances, reordered/missing entries or claimed execution authority still fails full replay, but a fully fabricated self-consistent history is not authenticated provenance.

Remaining dependencies for actual segmented application: a distinct database financial version and immutable persistence; transactional current control/source/ownership/dispatch/health/pool binding; concurrent retry/lease takeover; crash/lost-ack recovery; archive reachability and retention enforcement. Preserve old contracts and account histories. Ledger application and external submission flags stay false. No schema/dependency changes or main financial fixtures are required for this prerequisite.
