# Local finalization of an unsubmitted Paper request

Schema0017 adds an immutable `requested_paper_voids` fact and the internal `requested_finalization.finalize` operation. A current request can become `VOID_UNSUBMITTED` only when its durable local source-event history is empty. It releases its full cash/inventory reservation without changing cash, inventory, fees, basis or realized PnL. No SUBMIT, rejection, exchange cancellation, receipt or source seal is invented. Unfilled quantity remains the original requested quantity; cancelled quantity remains null.

Finalization and first submission share the PostgreSQL account lock. Their race has one winner. The operation checks the expected financial revision and stable command identity, stores the fact and clears the active request atomically. An exact retry returns the original result even if a later request exists; it cannot release that later reservation. Conflicting retries fail. Persisted facts cannot be updated or deleted. Failures before commit roll back; committed results survive process death and lost responses.

PAUSED, HALTED and STOPPED accounts may close an undispatched request, but finalization does not change their control state. Its clock must follow the current financial/control evidence. Any durable source event, including SUBMIT with unknown outcome, prevents this path and retains the hold. Submitted requests continue through existing source receipts and sealing. This proof means NO_DURABLE_LOCAL_SUBMIT in an engine that never dispatches externally; it does not prove the absence of an exchange order and cannot be transplanted into the separate submission laboratory.

Accounts with at least one void use `paper-requested-journal-v2`, `paper-requested-journal-export-v2` and `paper-requested-controls-export-v2`. Every financial request entry then includes a nullable `void`; total_finalizations counts local closures separately from source events. Financial revision counts requests, source events and voids. Complete offline replay checks the immutable frozen request, zero-event proof, expected revision, clocks, unchanged economic balances and all control checkpoints. Accounts without voids and previously captured exports retain their exact v1 formats. Request/source-event contracts and policy/control versions are unchanged.

The existing GET journal/controls endpoints dispatch both versions and remain read-only. Offline tools are `python -m scripts.verify_requested_journal FILE` and `python -m scripts.verify_requested_controls FILE`. Checksums establish internal consistency, not authenticated origin, freshness or signed completeness. The separate default-disabled local control-command endpoint is described in PAPER_REQUESTED_COMMANDS.md. No order mutation API, UI, scheduler, shared capital, human identity authorization, external submission or private reconciliation is added. Live stays disabled. Tests use isolated fixture databases; main receives no example balances or trades.

Current access boundary: PAPER_REQUESTED_COMMANDS.md describes the opt-in local control-command capability and its limitations. Local finalization and economic/source operations still have no HTTP write routes.
