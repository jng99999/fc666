# Scoped single-operator segmented ledger access

The existing PAPER_OPERATOR_TOKEN, PAPER_OPERATOR_ACCOUNTS and PAPER_OPERATOR_ACTIONS settings now support two distinct actions: READ_SEGMENTED_EVIDENCE and ENROLL_SEGMENTED_WORKER. Existing token format, exact bounded account/action lists and default-disabled behavior are preserved. No credential is generated, logged, exported or copied into the repository. Configure the actual token securely through environment settings, never in a URL or chat.

GET /api/v1/paper-segmented/evidence requires a Bearer token, explicit ledger_id query and READ_SEGMENTED_EVIDENCE grant for that exact ledger. scope defaults to financial; scope=operational returns complete financial-plus-local-worker evidence only when enrollment is declared. Responses use Cache-Control:no-store. This is access to evidence, never a current worker grant or authorization to submit an order.

POST /api/v1/paper-segmented/worker-enrollments requires ENROLL_SEGMENTED_WORKER and exact strict JSON fields ledger_id, command_id and expected_root_sha256. Enrollment compares the immutable root hash within the same account transaction and is allowed only before any financial command. Exact original retries acknowledge the original enrollment. Changed identity/checkpoint or retrospective enrollment fails without changing finances. Enrollment is irreversible and still does not create a lease, financial request, account or venue connection.

Disabled access returns503; missing/wrong credentials401; denied account/action403; missing ledger404; conflicting/unverifiable evidence409; database failure503. Errors are generic and omit internal exceptions, credentials and database connection details. Authentication and grants run before financial lookup. Input validation rejects extra fields, coercion and legacy ledger identities. No public create/claim/financial-command endpoint is provided.

This is the existing single configured operator capability, not multi-user identity, role management, persisted per-user grants, token rotation/revocation coordination or scheduler admission. Internal worker identities remain trusted strings. Full operator_worker_binding_supported and external_submission_allowed remain false until the remaining source/control/health/pool/scheduler gates are implemented. Secure public deployment and actual operator configuration are separate requirements; main settings remain unchanged during development.

The core worker enrollment library accepts an optional expected_root_sha256 for authenticated callers while preserving existing trusted internal calls. MissingLedger is a ValueError subtype so unknown ledger lookup has an explicit HTTP404 mapping without inspecting exception text. Existing financial/worker archive contracts and schema0028 are unchanged.

Restart only owned API for these source changes using scripts/dev_services.py helpers; existing start instructions and readiness checks remain applicable. No database migration, dependency, frontend build, new service or network rule is required. Tests use isolated PostgreSQL fixtures and clearly artificial test-only tokens. Never enroll main ledgers to demonstrate the API.

Process-local replacement: trusted embedded administration may call `app.state.segmented_operator_access.replace(validated_settings, expected_revision=N)`. Revision starts at0; replacement is all-or-nothing and rejects stale/non-integer revisions or invalid settings. Policies copy account/action sets rather than retaining mutable caller lists. No public management route, token display or user-facing credential transport is supplied.

Both segmented routes recheck credentials and account/action grants atomically immediately before the operation. The process policy lock remains held through evidence capture or enrollment transaction, so replacement waits for earlier admitted operations and all subsequently admitted operations use the new policy. A successful transaction ordered before replacement is not cancelled or undone. Same-thread replacement inside its own operation is rejected, and exceptional operations release the lock. This serializes these operator operations within this API process; sustained-load acceptance remains pending.

Replacement applies only to these segmented routes in one API process. Existing legacy command routes still use their existing startup policy. Other API replicas, worker processes and distributed deployments are not synchronised. Replacement is in-memory and does not save credentials, settings or a durable revocation record; a restart restores securely configured startup policy. Durable changes therefore still require updating protected configuration and rolling out every affected process. Non-operator Settings fields passed to replace do not reconfigure databases or services. This primitive does not close persistent grant/revocation or complete authenticated identity integration.

Persistent deny enforcement under schema0029 now supplements process-local replacement for these two segmented endpoints; see SEGMENTED_DURABLE_REVOCATION.md. API construction passes the database engine to Access, so committed database revocations remain effective after restart. Process-local replace still does not save allow-grant configuration or synchronise allow policies; it cannot undo a durable deny. The existing requested-Paper protected POST routes now also enforce global credential denies; segmented scoped denies and process-local replacement remain separate from legacy allow policy. See REQUESTED_OPERATOR_REVOCATION.md.
