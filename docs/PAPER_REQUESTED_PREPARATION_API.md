# Atomic local request preparation

POST /api/v1/paper-requested/preparation-commands adds the independent PREPARE operator action. It is default-disabled, requires exact account membership and header bearer authentication, and is not implied by ENROLL, PREVIEW_PREPARE, control or void grants. PREPARE does not grant access to the preview route, nor submit an order. Existing secure configuration guidance applies. Main has no token/grant/account installed.

The strict body contains every field of the existing preparation proposal plus preview_sha256 (64 lower-case hexadecimal characters). It contains no caller base, event, receipt or balance. Obtain a complete preview through the separately granted preview route or equivalent verified local artifact. The digest binds a snapshot/proposal; it is not a signed server token, a human approval receipt or proof that the preview endpoint was called. Actual write authority comes from the current PREPARE grant.

New preparation audits complete financial/control history under the shared PostgreSQL account lock, requires CONTROLLED enrollment, reconstructs the server-based preview and checks both requested revisions and its exact digest. It then uses the original journal's unchanged preparation logic within that transaction to persist one immutable request and admission, full cash/inventory reservation and financial revision. No read-unlock-then-write gap. Risk/state/funding/step/tick/time/capacity checks are rerun against that checkpoint. Changed proposals/digests, control changes or new economic activity invalidate stale previews. Two distinct concurrent requests cannot both reserve; two exact retries produce one reservation. Two-second lock_timeout bounds database lock waits, not whole-request duration.

Retries audit current evidence first, then reconstruct the immutable pre-request financial prefix and selected control prefix using the stored PREPARE admission's financial/control checkpoints. Previously sealed/voided requests, opening balances, source events, immutable policy and command chain reproduce the original preview. Financial v1 prefixes remain v1 even if later voids upgraded the current journal to v2. Any changed identity/proposal/clock/version/digest fails; older unmanaged requests without a controlled PREPARE admission cannot be reinterpreted as controlled preparation.

An exact retry remains valid after pause/STOP, fills, sealing, local void or a subsequent request. It acknowledges the original committed preparation only; it performs no new writes, reactivation, release or reserve. A matching request initially prepared by the trusted internal library can also be acknowledged if its full immutable evidence reconstructs this exact preview. There is no separate HTTP-origin or per-actor audit fact.

The response version paper-requested-preparation-command-result-v1 contains the frozen request, accepted_preview_sha256, initial_funding, preparation_committed=true and external_submission_allowed=false. Initial funding is historical acknowledgement, not current account availability or assurance that the old reservation remains active. Read the existing journal/controls exports for current state. The digest and acknowledgement are derived from existing immutable request/admission facts; schema0017 and financial/export versions remain unchanged. Original internal prepare callers and their current-summary retry semantics are preserved.

Disabled503, authentication401 and grant403 precede storage. Authorized missing account404; stale/conflicting/risk/unverified evidence409 and database/lock failures503 return generic no-store responses. Strict body errors use standard422 behavior. Rollback before commit saves no partial request/gate/hold. Genuine process death after commit with a lost reply reopens/retries with one effect. Account monetary balances, fees, basis and realized PnL remain unchanged at preparation; BUY reserves full limit notional plus ceiling fee, SELL reserves full quantity.

This is local Paper reservation, not exchange submission, source ingestion, an execution scheduler, shared capital or multiuser identity. Caller market rules remain explicit local simulation inputs. No SUBMIT/source event is invented. Pending unknown outcomes and existing late-fill/seal behavior remain unchanged. Live stays disabled.
