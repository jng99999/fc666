# Independent segmented local financial ledger

`paper-segmented-local-ledger-v1` persists a distinct local simulated financial namespace in PostgreSQL. It never imports old account balances, rewrites frozen v1/v2 history, joins capital pools or enables external trading. Identities must start `segmented:`. The trusted internal library exposes create/read/execute only; no HTTP operator route, worker consumption or application UI is wired to it.

Schema0027 adds `segmented_paper_ledgers` (audited current financial cache/head) and `segmented_paper_commits` (immutable full account snapshots and original commands). A root binds the explicit simulated opening; every subsequent node binds its predecessor, original command/checkpoint, financial revision and complete independently replayed account state. The cache cannot change root or skip a commit; database triggers reject commit updates/deletion and ledger deletion. Reads verify every retained node and financial transition, rather than trusting the cache or a head hash. Missing/corrupt evidence blocks reads, new commands and retries. Populated downgrade refuses to discard financial evidence.

Commands contain exactly command_id, kind, expected_sha256, expected_revision and payload. expected_sha256 is the current ledger node hash, and expected_revision is its financial revision. PREPARE accepts a frozen explicit request with the correct settled account base; APPEND accepts request_id and a bounded batch for the active request; VOID accepts the original zero-source local withdrawal receipt. A new command must match the current checkpoint. Original command retries return the original committed snapshot after full current-chain validation; changed payload/checkpoint under the same command identity is rejected. This historical acknowledgement never releases a later hold. A duplicate batch under a new identity is rejected rather than creating a new financial commit.

Account replay preserves100-request/8192-total-event/32MiB bounds; batches have128-event/128KiB limits including checkpoints. Persistence separately caps each full-snapshot commit at34MiB, retained database JSON at64MiB and512 commits per ledger, with at most100 ledgers. These are simultaneous bounds; retained storage/commit capacity may exhaust before the event limit. Exhaustion fails without losing balances/holds and does not guarantee future settlement capacity. No automatic compaction, deletion, infinite retention or assured terminal capacity is implemented. The old PostgreSQL journal remains capped at1000 events; this new namespace has its own contract.

One PostgreSQL account lock and transaction commit immutable evidence and cache together. Conflicting concurrent commands cannot mix effects. SIGKILL before commit leaves no new financial effect; SIGKILL after commit leaves exactly one effect and original retry acknowledges it. Tests use isolated databases, genuine process termination and a populated custom backup/restore, including all table-content hashes and full ledger replay after restoration. This establishes local process/restore acceptance, not power-loss, infrastructure failover or independent offsite durability.

Reported `local_financial_persistence_supported=true` applies to this internal local ledger only; `operator_worker_binding_supported=false` and `external_submission_allowed=false` are explicit. Embedded replay reports remain consistency artifacts, not authorization. Do not connect this primitive to public/controlled trading until current identity/grants, source provenance, owner/dispatch/health/pool bindings and scheduler admission are implemented and tested under a separate contract/version. Live remains disabled. Complete financial evidence archive: `paper-segmented-local-ledger-archive-v1` captures all root-to-head immutable commits under the same account lock and full database audit. Offline verification reconstructs every financial transition, checks identity, original command checkpoints, unique command IDs, contiguous predecessors, endpoints and hashes, and rejects resealed settlement changes or authority flags. It retains the ledger count/byte bounds; this is consistency evidence, not authentication, current authorization or an operational archive.

Capture: `.venv/bin/python -m scripts.capture_segmented_ledger --ledger-id segmented:YOUR_ID --output /protected/new-file.json`. The destination must be new, cannot be a symlink, and is created mode0600 with file fsync. Verify offline: `.venv/bin/python -m scripts.verify_segmented_ledger /protected/new-file.json`. The verifier does not load database settings or connect to PostgreSQL; JSON duplicate keys/nonfinite constants and oversized input fail. No automatic retention, restore/import command, independent offsite durability or worker grants are supplied.
