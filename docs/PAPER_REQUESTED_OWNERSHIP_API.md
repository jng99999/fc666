# Scoped local ownership commands

POST /api/v1/paper-requested/ownership-commands and /api/v1/paper-requested/owned-source-commands use the existing default-disabled single local operator bearer capability. Exact account membership and independent CLAIM_OWNERSHIP/DELIVER_OWNED_EVENT grants are required before storage. Neither implies the other, PREVIEW_EVENT or INGEST_EVENT. An owner label is local coordination data, not authenticated human identity. No production token/grant or main fixture account is installed.

The strict claim body contains account_id, request_id, owner, ttl_seconds(1..60), expected_financial_revision, expected_control_revision and expected_token(0..64). First claim expects token0; takeover expects the latest stored token and current financial/control revisions. All checks and claim insertion share the account row transaction. Submitted/unowned histories cannot be retrospectively enrolled. Expiry alone permits takeover, with the next token. Ownership creates no funds, reservations or financial/control revision advance and does not authorize submission.

Exact retry of the current active/unexpired claim uses its original revisions, duration, owner and preceding token and returns the original accepted_claim even after later activity in the same active request. This reconstructs consistency from durable claim fields, not proof of a prior HTTP invocation. Expired or superseded old claim proposals conflict; refresh complete state before takeover. A current-state request by the same owner may acknowledge the existing unexpired claim with its unchanged duration, but cannot extend it. Changed duration, stale fresh versions or wrong tokens conflict. Closed requests cannot be reclaimed. The claim_committed=true response acknowledges a saved claim; its original expiry is not an assurance of future validity.

The strict owned-source body is the source-event proposal and preview_sha256 plus owner and ownership_token(1..64). DELIVER_OWNED_EVENT permits explicitly labeled LOCAL_PAPER_OPERATOR_INPUT only. The server strips ownership fields before validating the original preview and source receipt. Current owner/token/expiry is checked before and after work; source, event, applicable SUBMIT gate, fencing timestamp and settlement commit atomically. Processing expiry rolls back every effect. Existing dual-version/risk/funding gates remain active. Original source retries require current unexpired ownership but acknowledge the initial receipt without another event/fill or changed original event token. Ordinary INGEST_EVENT continues to reject claimed requests.

Local SUBMIT remains a simulation fact, not external dispatch evidence. UNKNOWN_SUBMISSION retains full holds; valid submitted-request late fills remain acceptable after STOP. None of these routes sends an exchange order, queries a private venue or permits absence-based retry. Claim and delivery provide no human identity/audit, shared capital or scheduler. SQLite submission laboratories remain separate. Next: uniquely durable local dispatch evidence and unknown-result query-before-retry contract before transport integration.

Errors are503 when commands are disabled/unavailable,401 for missing/wrong authentication,403 for missing account/action grants,422 for malformed strict fields,404 for an unknown granted account and409 for stale/conflicting/unverifiable state. Responses use no-store and generic error messages without partial evidence. Read GET ownership and its offline verifier for complete histories; the original recovery-v1 view stays frozen. Token secrecy is not the authorization boundary: the server bearer and explicit grants are required.

Schema remains0019; existing unfenced library claim callers preserve their former signature/default behavior. Optional library claim fences require all three strict values together. No dependency, credential, network, UI or topology change. Preserve checkout/branch, .env/volumes/proxy/CA; normal startup is bash scripts/start.sh, and only the owned API needs restarting for this slice. Main remains empty/default-disabled, five services ready and Live off. Saved startup instructions are a draft, separate from publication/new-task restoration.
