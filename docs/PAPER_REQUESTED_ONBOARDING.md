# Scoped account enrollment and read-only funding preview

Two default-disabled operator routes extend the existing requested-quantity account namespace. ENROLL and PREVIEW_PREPARE are separate explicit actions in PAPER_OPERATOR_ACTIONS; neither is implied by control or void permissions. Exact account grants and header bearer authentication precede storage access. Existing secure-token/configuration guidance in PAPER_REQUESTED_COMMANDS.md applies. Main remains disabled and no token or fixture account is installed.

POST /api/v1/paper-requested/enrollment-commands accepts account_id, stable command_id, expected_financial_revision (strict integer>=0), aware created_at and an exact limits object: allowed_sides, max_order_quantity, max_request_notional, max_buy_inventory_quantity, max_fee_rate and min_cash_after_buy. Numeric limits are Decimal strings. The authorized operator explicitly chooses all limits; there is no implicit policy default or externally approved risk authority. The account must already exist and have no active request. Registration freezes its immutable local policy and starts PAUSED, without changing financial revision/balances. Activating it requires a separately granted existing RESUME command. The expected financial checkpoint is checked under the same account lock as preparation, so concurrent registration/preparation cannot both admit at that checkpoint. Original internal callers retain their optional-fence behavior.

An exact enrollment retry matches original policy/command/clock/financial checkpoint even after later activity. The response version paper-requested-enrollment-command-result-v1 contains the immutable accepted_enrollment and the current verified controls view. A conflicting retry fails; immutable policies cannot be revised through this endpoint. HTTP enrollment sets a two-second database lock timeout; it does not bound whole-request duration. Stored v1 enrollment facts already contain the financial checkpoint, so schema0017/export versions remain unchanged.

POST /api/v1/paper-requested/preparation-previews accepts account_id, unused client_request_id, expected_financial_revision (strict integer>=0), expected_control_revision (>=1), side, requested_quantity, limit_price, max_fee_rate, rules and aware created_at. Decimal amounts are strings. Exact rules are tick_size, quantity_step, min_quantity and min_notional. The base balance is always the server's audited opening/request/event/void history; supplying base or extra fields fails422. Proposed market rules are explicit caller inputs for local simulation, not fetched exchange constraints or verified current venue metadata.

The preview reads financial and control history together under the account lock, checks both revisions and explicitly controlled coverage, no active request, unused identity and remaining request capacity. It recomputes full-quantity funding, step/tick/minimum rules, clocks and the existing immutable policy's PREPARE admission. PAUSED/STOPPED deny previews; HALTED permits qualifying SELL only. A BUY of4 at100 with fee ceiling0.01 projects cash reservation404 and available cash596 from1000. SELL4 from inventory10 projects quantity reservation4 and available quantity6, without cash/fees/basis/PnL mutation.

The report version paper-requested-preparation-preview-v1 contains complete financial export, verified controls, proposal, server-based frozen request, calculated admission and projected_summary, plus reservation_created=false and external_submission_allowed=false. No request, admission row, reservation, event or balance change is persisted. CREATED and reserved amounts in projected_summary describe a hypothetical preparation only. Repeated previews may return the same report without consuming an identity. A preview can become stale immediately after its locked snapshot; it is neither a reservation nor authority to dispatch, and any future write must recheck both versions/policy/funding inside its own transaction. Pending/used identities are conflicts even if the existing internal prepare operation would treat an exact old request as a retry.

Offline verification uses python -m scripts.verify_requested_preview FILE. It reconstructs financial/control histories, both checkpoint values, server base, frozen request, admission and every projected amount. Duplicate JSON keys, unsupported versions, over32MiB reports, changed summaries and rehashed inconsistent facts fail. The report hash establishes internal consistency, not signed origin, current account freshness or authenticated completeness. Complete internally consistent substituted histories cannot be authenticated by this verifier.

For both routes: disabled503, authentication401, grant403, authorized missing account404, clock/rule/funding/state/version/evidence conflict409 and database/lock failure503 return generic messages with no-store. Strict body errors retain standard FastAPI422 behavior. There is no balance/account creation API, request submission/source-ingestion API, scheduler, multiuser actor identity, shared capital or Live trading. Existing financial/control snapshots and old routes remain compatible. The separately granted atomic preparation command is now implemented; see PAPER_REQUESTED_PREPARATION_API.md. Submission and source-event mutation remain absent.
